# Host 等待优化与复测（2026-10-23）

完成 16,000 次延迟样本：完整 DLL → SED → Service 共 11,200 次，包含旧版对照 3,200 次；独立真实 Named Pipe → Service 共 4,800 次。所有完整轮次丢弃为 0，连接 generation=1。额外的 128 条诊断协议验证不计入延迟样本。终点均为 mock PLAY 完成，不包含真实 HID/I²C、MCU 或机械起振。

## 实现的改动

- 固定容量为 8 的队列替代动态 deque，保持 FIFO、队列满丢弃与 50ms 过期策略。
- 提交端释放队列锁后再唤醒 worker；健康告警日志移到锁外；统计重置不再同时占用输入锁和统计锁。
- 新增默认关闭的 `--latency-trace`，真实 HID 模式也可使用；保留 `--mock --mock-trace`。
- trace 保留原有 samples 和 stage_samples，并新增等待阶段、线程 ID 与完成类型。
- 控制响应缓冲扩大到 64KiB，采用消息读取模式，修复新增诊断超过旧 16KiB 上限后被截断的问题。
- 保持专用线程 AboveNormal、进程 Normal，不绑核、不忙等，不修改全局电源、定时器或 GC 设置。

## 新计时能说明什么

首轮最慢事件 DLL→mock 为 25.635ms：Pipe 写入入口→Service submit 为 12.091ms，Service submit→取出为 13.425ms。其中提交端获取锁约 2µs，工作线程取队列锁不足 1µs，入队时间戳→取出为 13.423ms。这次主要等待并非这两次队列锁竞争。

worker 的 wait 返回时间包含条件变量重新获取锁；入队时间戳位于固定队列 push 前。应用层时间戳无法单独区分 Windows 就绪后等待 CPU、条件变量内部等待和线程其他位置的停顿，仍需内核轨迹定位。当前账户启动 WPR 返回 Access denied（0x80070005），没有修改系统策略，也没有遗留录制会话。操作步骤见 [内核采集权限说明](KERNEL_CAPTURE_PERMISSIONS.md)。
