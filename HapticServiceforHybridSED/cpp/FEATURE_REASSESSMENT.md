# 新架构功能重新评估（2026-10-22）

> 此文是实施前评估。建议的核心能力现已补齐，当前行为和命令以 [本轮功能补齐](SERVICE_UPGRADE.md) 为准。

本次为代码审查与方案评估，不代表下列建议均已实现。新 C++ 版最初以打通核心触觉链路为范围，未完整迁移旧版；不能把所有未迁移项都称为不需要。

| 原能力 | 新架构结论 | 不保留或未迁移的影响 |
|---|---|---|
| Windows 默认 OSK/TabTip 启动、窗口命中与来源推断 | 被 OSK_Prototype + HybridSED 替代，无需迁移 | 新版不再支持独立监听默认 OSK；来源由约定标记判断 |
| PLAY 优先于后台心跳/查询；依据最近 HID I/O 抑制轻量保活 | 应迁移，当前尚未迁移 | 到期后台 I/O 可能先占用串行 HID 线程，增加尾延迟 |
| 核心健康状态、故障分类、MCU accepted/rejected/I²C 错误读取 | 应补齐 | 仅凭 write 成功或 SESSION_OPEN 无法证明 MCU 接受并执行了 PLAY |
| 队列等待、HID 耗时、p95/p99、失败计数 | 性能验收必需，当前不完整 | 无法定位延迟阶段，也无法量化新旧差异 |
| 日志轮转 | 长期常驻部署应补齐 | 不影响单次协议正确性，但日志无上限会消耗磁盘并增加维护风险 |
| 运行中波形/强度设置与状态查询 | 产品若需设置界面则应补齐；固定配置验证可暂缓 | 当前只能通过启动参数改变，通常需要重启服务 |
| 原 JSON 传输格式与每键请求/响应 | 不必原样迁移 | 应保留必要控制能力，可另设低频控制面；不需给每个 PLAY 增加 JSON 往返 |
| Feature/interrupt 自动选择 | 有多固件/多平台兼容需求时应补齐 | 当前仅支持 Feature 能力正常的设备，旧版能连接的部分设备可能无法使用 |
| write-only 降级 | 不建议无条件自动开启；可作为显式诊断模式 | 缺少回读时新版拒绝就绪，避免把无法确认状态误报为正常 |
| 诊断 GUI 的具体 UI | 非核心执行所必需 | 可用 CLI/独立工具替代，但诊断接口和数据仍需保留 |
| Session/心跳/重连/过期丢弃 | 已有核心实现，仍需实机回归 | 现有 mock 无法证明物理 I²C、AW、休眠恢复和机械振动 |

## 心跳与延迟

当前 Worker 每轮先检查到期心跳，再取 PLAY。同一线程串行调用 WriteFile 与同步 HidD_GetFeature，所以心跳、尤其 10s 周期的 Feature 查询，可能延后已排队或随后到达的 PLAY。250ms 表示发送间隔，不是每次阻塞 250ms；实际增加多少取决于 I/O 时长，尚无硬件测量结果。

旧 `_DeferredHandler._acquire_io` 有 PLAY 等待优先与后台跳过机制，`keep_transport_awake` 还检查距离最近一次 HID I/O 是否超过 250ms。新 C++ Worker 目前未实现这两点，是需要补齐的调度差异。即使迁移优先级，已经开始的 I/O 也不能保证被后来到达的 PLAY 抢占。

250ms 轻量 HEARTBEAT 不是固件会话保活的必要周期：固件约 30s fail-safe，原约定验证心跳为 10s。250ms 是 Host 侧尝试避免 HID/I²C 传输空闲唤醒成本的策略，不是确认过的通用最优值。建议可配置、只在空闲时执行，PLAY 及控制命令更新最近 I/O 时间；接近保活截止时仍需防止后台验证永久饿死。

实机对比关闭轻量保活、250ms 与更长周期，记录空闲首键、持续输入 p50/p95/p99、HID/Feature 调用耗时及功耗。未测量前不能断言取消它一定更快，也不能断言现有频率一定无影响。

## 3s 重连到底指什么

- HID 工作线程：设备未枚举、句柄打开失败、能力不兼容、OPEN/预热失败、配置回读失败、写入错误/超时、周期 Feature 调用失败或确认 session 已关闭，均可能进入异常路径，释放句柄并等约 3s 后重新尝试。这不是精确故障检测周期，也不是只指 MCU 内部的 I²C error。
- HybridSED -> Service 命名管道：不是 3s HID 重连逻辑。Service 等待新的客户端；SED 后台写失败丢弃该请求，后续请求再尝试连接。不会在无按键时自动重播旧请求。
- MCU 内部 AW I²C 错误、PLAY 被拒绝等，不一定会成为 Windows WriteFile 错误。新版 PLAY 不等待逐条 ACK，周期检查也主要验证 session，尚不能保证识别所有内部硬件故障；需补充低频状态和计数器诊断。

## Host 异常退出与 30s fail-safe

这里的 Host 指持有 MCU 会话并发送心跳的 C++ Service，不是泛指任意 PC 程序。

可能停止心跳的情形：未处理异常导致 Service 崩溃、任务管理器或 taskkill 强杀、服务进程挂死、HID 线程被驱动调用卡住、Windows 蓝屏/硬复位、整机突然断电但 MCU 仍有独立电源、总线或驱动故障导致所有心跳无法到达。

这些不全是“进程退出”，共同点是 MCU 收不到后续心跳。MCU 若也断电就无须等待 fail-safe；若 MCU 主循环自身卡死，依赖主循环的会话 fail-safe 也不能代替独立 watchdog。

仅 OSK 或 HybridSED 崩溃/关闭时，Service 仍运行并继续心跳，当前不会触发该 30s 关闭机制。正常 SCM stop/Ctrl+C 会尝试 CLOSE，fail-safe 是命令未送达时的兜底，不能承诺正常停止一定写入成功。

## Session 归属与 .NET

后台常驻、服务运行期间保温的当前策略下，SESSION_OPEN/CLOSE/HEARTBEAT 全由 C++ Service 管理，HybridSED 不需要发这些命令，也不应有第二个 MCU session owner。

如果以后希望 OSK 关闭后节能，需增加“是否需要触觉”的业务状态或可配置空闲策略。上游可发业务启停通知，仍由 Service 统一映射为 MCU 会话命令，不需要上游直接控制 HID。

本地项目目标框架已核对：C# SemanticEventDispatcher 是 net8.0；原 C# HapticPipeConsumer 是 net10.0，不是 net8.0。C++ Service 不依赖 .NET；OSK_Prototype 自己仍需要 .NET 10 Windows Desktop Runtime。用 C++ 替换 Consumer 不会消除 OSK 和 HybridSED 的 .NET 需求。

## 当前优先级建议

先补 PLAY 优先/后台调度与性能计数、核心状态/错误分类和日志轮转，再做 SCM/睡眠/断线实机验收。动态控制面按产品设置需求补齐；兼容性模式按目标固件能力决定；原 OSK 来源检测和逐键 JSON 路径不回迁。

本次没有更改 250ms 参数或调度实现，以免把尚未做 A/B 实测的策略当作已验证优化。
