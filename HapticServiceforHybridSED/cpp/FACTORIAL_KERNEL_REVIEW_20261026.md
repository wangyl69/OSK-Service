# 四组合对照和同轮线程调度分析

## 结论

四组合真实 DLL 软件测试共 11,200 次完成，零丢弃、零额外/松开 PLAY。四组 Pipe＋Service 均没有 >5ms；旧 SED＋旧 Service 的正常负载轮有四个 DLL→mock >5ms，其中两个 SED 队列分别为 5.438ms、10.611ms。因此长尾并非新版独有，不能因为此前新版捕获慢样本就断定改动造成回归，也不能凭这轮新版通过断定已消除。

已有正常负载内核采集中最慢事件的通知很快到达 ReadyThread，但线程 Ready 后等待约 3.723ms 才首次运行。这是针对该事件的直接调度证据；不外推至没有同轮 ETL 的 36ms 旧事件。

## 完整性检查与原因分析的区别

完整性检查只确认 WPR 启动/停止成功、ETL 可解码、记录的事件丢失数为零。它不能直接说明某次按键等待的原因。之前的 `tracerpt` 摘要把 Thread opcode 36/version 5 显示为编号，尚未解析它的线程切换字段。

本轮新增离线工具 `tools/EtlSchedule`，使用微软 TraceEvent 4.0.0 从同一 ETL 解码：2,333,060 个 CSwitch、1,200,905 个 ReadyThread，保留输入线程和工作线程相关事件 57,753 条。它不负责采集，不需要提升生产 Service 优先级，不给生产 Service 增加 .NET 依赖；工具本身需要 .NET 10 SDK 和 NuGet 依赖。

原始 QPC tick 按 `capture.json` 的 10MHz 频率换算到应用 QPC 微秒，不能仅按墙钟或相近日志行配对。这里明确使用原始 QPC；TraceEvent 提示推荐相对时间的警告不影响此处与应用原始计数器的对齐目的。

## 同轮实际时间线

分析对象：`logs/real-pipeline-schedule-20261026-142450-e938924e/`，之前完成的 1,410 次正常负载连续会话。该轮没有 >5ms 事件，以下取三个最慢 Pipe＋Service 事件。

| 测量键索引 | Pipe＋Service ms | 通知→Ready µs | Ready→首次运行 µs |
|---|---:|---:|---:|
| 1134 | 3.777 | 2.6 | 3723.3 |
| 516 | 3.128 | 2.1 | 3069.9 |
| 1030 | 3.059 | 2.9 | 2697.6 |

索引1134的 Service 工作线程 ID 为41100：

* 通知入口 QPC µs：467526037077。
* ReadyThread：467526037079.6。
* CSwitch 切入工作线程：467526040802.9，CPU10。
* 应用等待函数返回：467526040813。
* 获取队列锁：467526040816（请求取锁在467526040814）。

线程很快被标记为可运行，主要等待发生在 Ready 后、首次运行之前。索引1030还在首次运行后被切出为 Ready，再次切入才返回应用等待；不能只拿首次切入时间当成应用继续执行的时间。

本轮完成了上述线程状态与切换时刻的关联，没有解析符号化调用栈、逐 CPU 全部竞争线程及每次 DPC/ISR 的归属；不能断言竞争的具体进程/驱动，更不能声称已查明之前36ms长尾。无依据继续改队列锁或提高到实时优先级。

离线复现：

```powershell
dotnet run --project HapticServiceforHybridSED/cpp/tools/EtlSchedule -- HapticServiceforHybridSED/cpp/logs/real-pipeline-schedule-20261026-142450-e938924e
```

生成 `kernel-thread-events.json`；本次筛选的十个最慢事件窗口另存 `kernel-correlated-events.json`。Ready/CSwitch 数据由微软库解码，部分枚举原因仍为数字；未知原因不自行赋予含义。

## 四组合的用途和实际执行

旧版仅作为实验对照，不是建议日常退回旧版。整套新旧同时切换不能区分 SED 与 Service 改动的作用，故将两个因素拆开。脚本 `tests/check_wait_path_abba.py --factorial` 每个负载执行四种组合、每种1,400次，压力轮反转顺序，全部真实 DLL/Hook/SED/Pipe→mock PLAY。每轮单独一次预热不计入1,400，全部保留SHA256、命令和结果。

| SED / Service | 正常 Pipe＋Service P99 / 最大 ms | 四进程压力 P99 / 最大 ms |
|---|---:|---:|
| 旧 / 旧 | 1.232 / 4.553 | 0.354 / 0.743 |
| 旧 / 新 | 1.121 / 3.371 | 0.224 / 0.835 |
| 新 / 旧 | 0.651 / 4.098 | 0.716 / 2.661 |
| 新 / 新 | 0.729 / 2.006 | 0.522 / 4.015 |

每格1,400次；Pipe＋Service均0次>5ms。旧/旧正常轮DLL→mock最大11.344ms，另外三组合正常轮最大4.562/4.225/4.679ms。每个格子只有一轮，反向顺序和负载仍不能控制全部后台活动，且当前新版Service包含开启的额外通知诊断开销。不能据此宣称某组合优于其他组合，更不能将压力下更快解释为压力有益。

四个旧/旧正常轮的 DLL→mock 慢事件分别5.301、5.734、11.344、8.171ms，来自不同批次；其中5.301ms由多个各自低于5ms的区间累加。样本没有遗漏，`slow-events.json`按全链路及各段阈值筛选，不能误报成四个 Pipe＋Service 超标。

## 证据与边界

* 四组合：`logs/wait-factorial-20261026-144027/manifest.json`、`stages.csv`、`slow-events.json`。
* [四组合分段CSV](FACTORIAL_STAGES_20261026.csv)：单位µs，每组P50/P99/最大值及>5ms次数。
* 同轮内核分析使用之前保存的ETL，没有把本次四组合与另一轮ETL拼接归因。
* 仍无真实 MCU、HID/I²C 和振动耗时；无绑核、无500Hz过载、无优先级提高；本轮未修改生产算法，也未提交/推送。

可以继续使用新版推进硬件联调。下一步若追查极端长尾，应在可重复慢场景保留同轮轨迹，再分析具体竞争线程及中断，而非用持续追加相同压测证明不存在长尾。当前可以报告分段分布和观测最大值，不能提供硬实时上限。
